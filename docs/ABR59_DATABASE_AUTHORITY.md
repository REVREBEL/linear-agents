# ABR-59 M12 — Database authorization and production-safe persistence

## Observed host baseline (read-only, 2026-11-20 Pacific)

Ubuntu's active Percona PostgreSQL cluster reported **18.7**, socket port **5433**, dedicated database `agent_memory` (database owner `postgres`). The `memu` schema and its four tables (`alembic_version`, `recall_files`, `recall_file_segments`, `resources`) were owned by `bridge`, with no row-level security on either recall table. The schema revision was `20260703_0001`, pgvector 0.8.1, one legacy file and one segment, zero resources and zero bridge-receipt-named files. Only metadata and aggregate counts were queried; no memory text or credentials were read. `bridge` inherits the existing `agent_memory_app` group and is not a superuser or BYPASSRLS role, but table ownership alone defeats ordinary RLS. No production migration was applied.

The installed shared memU environment is 0.10-compatible and the normal CLI uses migration/create mode; its native library supports `ddl_mode=validate`. It commits file and segment changes via separate transactions, so an interrupted commit cannot be assumed to have rolled back.

## Authorization design

- Schema/table ownership belongs to the PostgreSQL operator, not an agent. Forced RLS protects the native recall tables. No general SELECT privilege is granted on resources, migration history, or the scope registry.
- Every trusted four-part scope maps to the existing native user hash (tenant/repository/issue) plus agent ID. The SHA-256 of the JSON pair generates a fixed 56-hex suffix; prefix `bmr_` for the reader and `bmw_` for the writer. The full native scope is stored in an operator-only mapping, so the role-name hash is not the authorization itself.
- Policies use the authenticated PostgreSQL `session_user`, not a claimed role, mutable GUC, or caller-provided scope. Both writer and reader can SELECT only their own bridge-named memory rows and matching segments. Reader cannot mutate; writer may insert the scoped native file/segments and update only file content, description, embedding and updated_at (native memU requires the update). Neither can delete, truncate, relabel, manage roles, perform schema DDL, or switch to another scope. The composite parent FK checks new non-null segment identities. A unique scoped name index prohibits duplicate bridge receipt file names.
- The operator-only Node factory fixes the socket, port and database and derives login identities from its authenticated job. Its commit validates exactly the claimed M11 native payload/digest and rejects an already-confirmed or repeated attempt. The native Python process authenticates directly with the distinct PostgreSQL writer, verifies privileges, scope mapping and forced RLS, refuses a preexisting row, calls memU 0.10's native `MemoryService.commit_results` in validate-only mode, and verifies persisted exact content/description and complete matching segment with 768-dimensional vectors. Embeddings use only the local Ollama endpoint. No arbitrary DSN, credential, command, embedding endpoint or subprocess environment comes from an agent.
- The durable M11 journal claim precedes native writes. Any timeout, unexpected response, incomplete row, process failure, or mismatch stays unconfirmed and requires operator reconciliation, without an automatic retry. The independent signed approval record authorizes recall only after the confirmed journal state. The reader's SQL restricts receipt IDs **before** text is fetched, requires the single expected matching native segment and both vector dimensions, and the adapter independently checks signed content and description and sanitizes the result. Raw SQL in a reader scope may see its own unapproved or partial rows, but those never enter the authorized recall envelope.

## Explicit rollout (after source review and separate operator approval)

1. Quiesce memory writers/readers; stop new legacy database sessions via an approved maintenance policy and drain existing clients. Inspect ownership, privileges, memberships, schema revision, client authentication, data count, native package version, and the root-controlled runtime installation. Capture a protected backup of the dedicated database plus matching role/membership definitions (database-only dumps do not recreate global roles); test restoration in an isolated instance. Keep backups private and do not publish credential material.
2. Apply `memory/migrations/002_memu_scope_authority.sql` as the PostgreSQL operator on the dedicated `agent_memory` socket, with `psql -X -v ON_ERROR_STOP=1`; the migration must run transactionally, fails on unexpected state or active client connections, and removes legacy agent ownership. Review any preflight mismatch before attempting again. The bridge service must remain inactive for the legacy memU write/recall path.
3. In the reviewed operator program derive identities using `restrictedDbIdentity(trustedJob.scope)`. Run `003_memu_scope_login.sql` as the operator with psql variables `reader`, `writer`, `user_id`, `agent_id` equal to the derived names and native identity fields. It creates disabled, passwordless scope logins with no role-management permissions. Never provision from an agent's requested scope.
4. Configure root-only peer authentication: add `local agent_memory +bridge_memory_reader,+bridge_memory_writer peer map=bridge_memory_authority` **before** the broad local peer rule. Follow with a local reject for these groups in other databases and host reject rules for both IPv4 and IPv6 before general host rules. In `pg_ident.conf` add explicit `bridge_memory_authority root <exact scope role>` lines for each approved reader and writer; no wildcard or agent OS identities. Validate PostgreSQL's parsed HBA/ident rules, reload, then enable LOGIN on the exact provisioned roles as the operator. Verify root peer connections to both scoped logins and that bridge/rebel cannot connect as them. Do not supply a password or grant agents membership in these roles. Peer mapping grants identity only at the local Unix socket.
5. Install an independently reviewed root-owned, non-agent-writable Node binary and pinned memU 0.10 Python runtime at `/var/lib/bridge-memory-authority-runtime/bin/python` including its complete dependencies; verify ownership and all symlink destinations and package integrity. Use the isolated reviewed root-owned source checkout from M11. The current shared `/opt` toolchain has agent-writable ancestors and is **not** the production authority runtime. Do not copy unreviewed mutable agent runtimes into a privileged environment. The factory fails if the executable, helper or authority directory is not trusted. Keep the operator credential directory mode 0700.
6. M13 may wire the restricted factory into the already authenticated job and M11 authority; M14 must separately approve live rollout. Validate the intended scope's direct DB role behavior and complete the signed promotion + fresh scoped recall canary before enabling the feature. Keep unapproved features disabled.

## Failure and operational rollback

Quiesce and block new scope connections, execute `004_memu_scope_disable.sql` as the operator, terminate any remaining scope sessions and remove corresponding peer mappings. Verify restricted logins cannot connect and row counts remain unchanged. Leave the forced policies, owner transfer, scope registry and native data intact. No unsafe fallback to the legacy owner role. If reverting schema or data is necessary, restore the protected pre-migration backup and matching global roles into a **separate** isolated database, validate and obtain explicit approval for any production cutover. Do not automatically replay an uncertain commit or overwrite legacy records; reconcile the durable journal and exact native file and segment evidence under operator review.
