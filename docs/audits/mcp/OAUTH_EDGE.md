# ABR-95 — MCP OAuth resource authorization and edge acceptance

**Status: independently tested local-only resource-server component, not a deployed identity service or public endpoint.** This PR extends the ABR-94 localhost proof. Production `agent-bridge.service`, `/jobs`, existing Worker OAuth, host enrollments, secrets, Tunnel, and Cloudflare DNS remain outside this change.

## Trust architecture and source boundaries

- The Bridge MCP process acts only as an **OAuth 2.1 resource server**. User authentication, authorization-code/PKCE enrollment, refresh-token issuance, and dynamic registration happen at an **independently trusted authorization server/IdP**. This PR intentionally does not add a production authorization server, user database, login flow or static bearer capability URL.
- `oauth-resource.mjs` accepts a server-owned trusted HTTPS issuer, exact HTTPS resource audience, reviewed ES256/RS256 public JWKS, explicitly authorized principals, client IDs, devices, tools and a real revocation lookup. Verified `at+jwt` signatures, exact issuer, singleton audience, expiration, not-before, issued-at, bounded lifetime, unique token ID, trusted client ID, subject grants and scopes are required **on every HTTP request/tool call**. JWKS are provided by operator configuration; no token-supplied keys, `jku`, dynamic key fetch or algorithm downgrade is allowed. Subject/client/device/tool grants cannot be expanded by token contents.
- The `oauthResource` parameter of `createLocalMcpRelay()` is optional: the old ABR-94 paired smoke continues to use its standalone test token untouched. An OAuth resource authorizer changes **only the localhost test relay**, not the running production Bridge server. `oauthResource` is an explicit object injected by the approved future host startup; no env variable implicitly enables OAuth mode.
- `scripts/fixtures/oauth-local-issuer.mjs` is a **test fixture only**. Its in-memory authorization flow exercises a disposable signing key, scoped DCR, exact redirect URI, explicit approval/consent, state, PKCE S256, issuer binding, resource indicator on authorize and token exchange, one-use codes, rotating one-use refresh tokens and immediate access-token revocation. It is **never** imported into the running server and must never be used with real end users.
- Protected resource metadata: unauthenticated `GET /.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` advertise the fixed configured resource URI, trusted issuer, supported scopes and header bearer requirement; calls to `POST /mcp` still require bearer authorization. The 401 challenge refers to the **configured HTTPS resource metadata**, not the origin's untrusted Host/Forwarded headers. Rejected requests do not disclose raw token bodies. Legacy test bearer mode does not auto-mint OAuth access.

## Protocol generations and acceptance

| Era | Implemented in this isolated fixture | Later integration requirement |
| --- | --- | --- |
| Modern **2026-07-28** | Per-request `_meta` version/client-capabilities, mirrored `MCP-Protocol-Version`, `Mcp-Method`, optional `Mcp-Name`, explicit stateless `server/discover`, no session grant, `resultType: complete`, per-response `_meta.serverInfo`, private zero-TTL listing hints, modern 400 `HeaderMismatch -32020`, unsupported-version `-32022`, method-unknown 404 `-32601` | True SDK-based end-to-end ChatGPT client negotiation, pinned SDK and full transport implementation including SSE/MRTR, request cancellation, header encoding, and subscription streams |
| Legacy **2025-11-25**, **2025-06-18** | `initialize` and per-call header version, legacy tool discovery/invocation with **the same OAuth resource validation**, no need for a separate OAuth bypass, 2025-06-18 ABR-94 proof unchanged | Full legacy session lifecycle and interoperability across proxy reconnects |
| Deprecated **2024-11-05** | Not implemented; no historical SSE GET/POST listener | Explicit opt-in only after separately reviewed compatibility requirements |

The protocol fixtures follow the official [MCP 2026-07-28 spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), and [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). The fixture does **not** claim complete conformance simply because it passes the listed sample requests. Modern requests never grant privileges based on `Mcp-Session-Id`. Unsupported legacy version codes are not incorrectly labeled AccessDenied/BackgroundTask/SessionExpired.

## Cloudflare and host routing — reviewed deployment plan, not an applied configuration

Proposed external URI: `https://mcp-bridge.revrebel.io/mcp` (resource audience matches exactly). The Ubuntu canonical Bridge runtime continues to bind `127.0.0.1:8788` for the already-authorized Linear `/jobs` API. **Do not route MCP through `/jobs`, reuse its bearer token, or expand its WAF allowlist.** The design uses a *separate* approved MCP process, runtime user, identity and loopback listener, with the existing Synology NAS reverse proxy route preserved for non-Tunnel inbound requests. A new Cloudflare Tunnel hostname to the new MCP loopback listener is a **proposal only**, conditional on inspection and explicit approval of the actual Tunnel route, DNS ownership, Zero Trust Access application and known host networking at the moment of deployment.

A future approved deployment should:
1. Allocate a separate MCP localhost bind and health endpoint; do not expose port 8788 or reuse existing Worker OAuth grant databases.
2. Configure a **single** canonical public resource URI, trusted IdP issuer/JWKS, explicit user-client-device scopes, revocation source and approved redirect URI(s). Use IdP OAuth Protected Resource Metadata, client-ID metadata or DCR only as actually supported by the authenticated IdP. Authorization response `iss` (RFC 9207), state, S256 verifier and resource indicator validation belong at client and IdP boundaries; do not pretend the resource server itself authenticates a user.
3. Route only the intended paths through Cloudflare Tunnel. Make protected-resource metadata reachable to authorized OAuth discovery clients **without opening tool calls**. If Cloudflare Access would intercept browser/OAuth discovery or token validation, scope an explicit policy: public metadata GET only, authenticated tool POST separately. Never broadly bypass Access on `/mcp`. Establish trusted proxy-header handling at the edge; this local harness rejects forwarded headers entirely.
4. Rate-limit tool calls and enforce per-device/per-user/tenant quotas in ABR-96–100; validate the separate Ubuntu `bridge` process identity, path and command sandbox, MAC service counterpart and real client handshake before cutover.
5. Prove endpoint reachability and real ChatGPT MCP client OAuth support in *approved staging*; do not assume a given ChatGPT plan has access. Record exact external client and IdP versions, auth consent scopes, callbacks, browser Origin, HTTP status, revocation effects and cancellation.
6. **Rollback:** disable the new MCP Tunnel ingress route, stop only the new MCP service, revoke the service's OAuth resource registration/tokens if necessary, and revert only its source branch. Preserve `agent-bridge.service`, the Synology NAS reverse proxy, existing Cloudflare Worker routes, Linear agent registrations and PostgreSQL memory data.

The current localhost-only HTTP Host/Origin checks deliberately reject spoofed `Forwarded`, `X-Forwarded-Host`, or `X-Forwarded-Proto` headers and require exact `127.0.0.1`; **they are not sufficient for a public HTTPS deployment**. A narrowly designed authenticated proxy boundary remains a required future gate.

## Verification

`node --test scripts/test-mcp-oauth.mjs` exercises generated ES256 test JWTs, PKCE/DCR/issuer/state/resource/redirect protections, refresh/replay and revocation, public metadata and protected calls, signed issuer/audience/time/subject/client checks, authorization narrowing, modern mirrored headers, stateless discovery, legacy initialization, no unauthenticated tool access, and spoofed forwarded header denial. `npm run mcp:foundation:test` preserves the 24 prior ABR-94 tests; the Worker/Bridge regression suite remains independently required.

### Deferred requirements

This PR does **not** provide a production login/consent service, opaque-token introspection, automatic key rotation/JWKS fetch, persistent revocation database, all MCP SDK transport extensions, real Cloudflare exposure, or real ChatGPT user authorization. Those depend on selected production IdP, client and network policies and must be independently validated in ABR-96–100 before deployment. The test-only fixture cannot be approved as a production authorization server.
